# dsh-fetch-third-party 插件设计框架 v2

> 状态：**框架 v2，待最终验收**。本文件吸收了一轮评审意见（服务商可配、预算上限、路线图），验收通过后进入开发。
>
> 一句话设计：**一个"第三方抓取服务"插件——抓取委托给用户自己配置的第三方服务（Tavily / n8n / 自建爬虫，不止一家），本机不直连目标网址；API key 单一写入托管保险箱；会话级抓取预算兜底；默认由 AI 保守决定抓取哪些搜索结果。**

## 0. 项目定位

| 项 | 值 |
|---|---|
| 项目名（目录） | `fetch` |
| **包名（更新）** | **`dsh-fetch-third-party`**（突出"第三方抓取服务"，不绑定单一厂商） |

## 1. 背景与需求（不变，简述）

- 官方 `web_fetch` 因 SSRF 防护 deferred 而禁用；"能搜不能抓"是行业现状（Codex 也如此）。
- 需求：模型能抓网页全文；安全（不碰内网）；key 绝不明文；**第三方服务由用户自选自填**。
- 结论：抓取委托第三方（"快递员模式"），本插件只负责"把请求转给用户配置的服务商，把结果接回来"。

## 3. 架构：契约 + 适配器（核心变化）

### 3.1 抓取契约 v1（本插件定义的标准接口）

为了让"用户自建的服务"（n8n 工作流、自写爬虫）也能接入，本插件定义一个**最小契约**，所有第三方服务要么原生适配（Tavily），要么按契约对接（n8n/自建）：

**契约请求**（插件 → 第三方服务）：

```
POST {baseURL}            （baseURL 由用户在卡片填写）
Content-Type: application/json
Authorization: Bearer {apiKey}     ← 标准传 key 方式（适配器可覆盖）
Body: { "url": "<要抓取的网址>" }
```

**契约响应**（第三方服务 → 插件，HTTP 200）：

```json
{
  "title": "可选，页面标题",
  "content": "页面正文文本（markdown 或纯文本）",
  "statusCode": 200
}
```

- 非 200 或不可解析 → 视为抓取失败（WebError 或带状态码的结果，按 seam 语义）。
- **自建爬虫 / n8n 工作流只要按这个契约收发，即可接入，无需改插件**。

### 3.2 适配器（内置两种 + 一种契约直连）

| 适配器 id | 适用 | 请求如何组装 | 响应如何归一化 |
|---|---|---|---|
| `tavily` | Tavily 官方 API | POST `{baseURL}/extract`，body 用 **Tavily 原生格式**（`{ urls: [...], api_key? }`） | 解析 Tavily 的 `results[]` → 契约/`WebFetchResult` |
| `n8n` | 用户自建的 n8n webhook | POST `{baseURL}`，body 按**契约**（`{ url }`，key 走 Bearer 或 n8n 工作流自行处理） | 期望 n8n 工作流返回契约 JSON |
| `custom` | 用户自写爬虫/任何 HTTP 服务 | POST `{baseURL}`，body 按**契约** | 期望返回契约 JSON |

- 用户在卡片选择适配器 → 决定请求组装与响应解析方式。
- 新增服务商 = 新增一个适配器模块（几十行），**不需要改核心逻辑**——这是"扩大兼容"（后续方向一）的机制基础。

### 3.3 提供方注册

- 插件以 `inject: ['web', 'credentials']` 挂载，向 `ctx.web.registerFetchProvider({ id: 'third-party', ... })` 注册。
- 每个请求：读配置（适配器、baseURL、key 引用）→ 解析凭据 → 调用适配器 → 归一化为 `WebFetchResult { url, statusCode, body, truncated }`。

### 3.4 数据流（通用版）

```
模型
 │  web_fetch_url({ url })            （方案 B 自带工具，见 §7）
 ▼
本插件工具 → ctx.web.fetch() → fetchProvider 'third-party'
 ▼
路由层（当前单提供方直连；多提供方见 §8）
 ▼
适配器（tavily / n8n / custom）
 ▼
第三方服务（Tavily 服务器 / 用户的 n8n / 用户的爬虫）→ 由它去访问目标网址
 ▼
归一化 → 模型看到正文
```

**安全不变**：本机只连"用户配置的第三方端点"，从不直连模型指定的目标网址。

## 4. API key 单一写入点（结论不变，细节微调）

- **唯一写入入口**：GUI 卡片 → 写入托管保险箱 `$DSH_HOME/.credentials.yaml`（0600、永不进 process.env、热重载）。
- 设置区块只存：key 的**引用名**（`apiKeyEnv`，可配，如 `TAVILY_API_KEY` / `N8N_API_KEY` / 用户自定义名）、接口地址、适配器、抓取上限。
- **多服务商时**：不同服务商各自的 key 仍在同一个保险箱，用不同引用名区分（集中审计不变）。
- 插件每请求 `ctx.credentials.resolve(credentialRef(apiKeyEnv))` 现取；无凭据服务时退回启动环境层；文档写明平台优先级（环境变量 > 保险箱 > .env）。
- 卡片 key 控件：只显示"已配置/未配置"，永不回显值（照抄官方 WebSearchCard）。

## 6. 抓取预算与"搜索-抓取"策略（新增，回应评审第 4 点）

### 6.1 默认策略：AI 保守决策

- **谁该抓、抓哪个，常态下交给 AI 判断**：模型的工具指引文案写明"**仅当搜索摘要不足以回答时，才对具体结果调用抓取**；不批量、不自动全抓"。
- 搜索与抓取天然衔接：`web_search`（官方 DeepSeek）返回结果+摘要 → AI 评估 → 对值得深挖的个别 URL 调 `web_fetch_url`。**不自动**"抓取前 K 条"——自动批量抓取明确列为**非默认**的未来可选项。

### 6.2 用户上限：会话级预算（本地强制）

- 配置项 `maxFetchesPerSession`（默认 `10`，卡片可调）。
- 插件按**会话**计数（成功与失败尝试都计入，防止刷失败绕过）。
- 达到上限后，该会话后续 `web_fetch_url` 调用**直接拒绝**，返回明确错误："已达本会话抓取上限 N，可在插件配置中调整"。
- 调高上限/新会话 → 立即生效（配置热重载）。

### 6.3 "上限怎么发给第三方"（评审疑问）——**不发，本地强制**

- 上限是**本插件的本地闸门**，不是发给第三方服务的参数——第三方服务不需要知道预算。
- 只有一种情况涉及"发送信息"：**批量型服务**（如 Tavily `/extract` 支持一次传多个 url）。处理：适配器按"剩余预算"分批发送，绝不超发；剩余 0 时直接拒绝，不发请求。
- 单 URL 服务（n8n/custom 契约）天然一次一个，无此问题。

### 6.4 计数口径

| 项 | 规则 |
|---|---|
| 计数维度 | 会话（Session） |
| 计数时机 | 每次工具调用 +1（含失败、超时） |
| 重置 | 新会话重置；调高上限即时生效 |
| 拒绝语义 | 明确错误信息，模型可基于已有信息回答或提示用户 |

## 7. 工具暴露（方案 B 确定）

- **自带工具**（`defineTool`），工具名建议 **`web_fetch_url`**（不叫 `web_fetch`，避免与官方未来工具撞名；不绑定厂商）——**名字待验收确认**。
- 工具 schema：`{ url: string }`（单 URL，保守策略）。
- 指引文案（写入工具描述，保守策略）：
  > 抓取指定网页的完整内容。**仅在搜索摘要不足以回答用户问题时使用**；一次只抓一个 URL；不要在已有足够信息时重复抓取。
- 方案 A（仅 Provider、对接官方 `web_fetch`）文档化为备用路径（需自定义 agent 预设），不在本轮实现。

## 8. 路由层（后续方向二，P3 预留）

当用户配置**多个抓取服务**时（如同时有 Tavily 与自建 n8n）：

- 插件支持注册多个"第三方服务实例"（每个实例 = 适配器 + baseURL + key 引用）。
- **路由策略**（待 P3 细化，先定原则）：
  - 配置指定优先实例；失败时按顺序回退到下一实例；
  - 或卡片让用户手动指定当前使用哪个（与卡片"服务商"字段衔接）。
- 路由层与卡片、适配器解耦：先有适配器与单实例，P3 再加选择/回退。

## 10. 工具流程（评审要求的交付物）

### 10.1 前置（一次性配置）

1. 用户安装插件（`dsh plugin --profile web add ...`）。
2. 卡片配置：选服务商（如 tavily）→ 填 API Key（写入保险箱）→ 确认地址（默认即可）→ 设上限（默认 10）。
3. 新建会话（让模型看到新工具）。

### 10.2 会话内流程（每次使用）

```
① 用户提问："帮我调研 XX"
② 模型 → web_search（官方 DeepSeek）→ 结果列表 + 摘要
③ 模型评估：摘要够用吗？
      ├─ 够 → 直接回答（不触发抓取，预算不动）
      └─ 不够且值得深挖 → web_fetch_url({ url })
④ 插件处理：
      a. 预算检查：会话计数 ≥ 上限？→ 拒绝："已达上限 N，可在插件配置调整"
      b. 路由 → 当前配置的第三方服务（P3 后：多实例选择/回退）
      c. 适配器按服务商组装请求（tavily 原生 / n8n 契约 / custom 契约）
      d. 凭据解析（每次现取，保险箱）
      e. 调用第三方 → 归一化正文 → 计数 +1
⑤ 模型基于正文回答，引用来源 URL
⑥ 达到上限后：工具拒绝 → 模型告知用户"已达上限"或基于已有信息作答
```

### 10.3 边界与异常

| 场景 | 行为 |
|---|---|
| 第三方服务超时/失败 | WebError → 模型可重试或换 URL（预算 +1 已计） |
| 第三方返回非契约内容 | 归一化失败 → 明确错误 |
| 用户调高上限 | 下次调用生效（热重载） |
| 批量服务（tavily 多 url） | 按剩余预算分批，绝不超发 |
| 多会话 | 各自独立计数 |

## 11. 安全边界与诚实说明（v1 保留 + 补充）

1. **模型仍能读本机文件**（沙箱只管写不管读，与官方同级别）；dsh 不给路径、key 不进 env，已是最佳实践。
2. **第三方信任边界**：用户自填的服务商会看到抓取 URL 与内容（Tavily 亦然）；自定义端点请指向可信服务，**不要填内网地址**（文档提示）。
3. **key 单一写入点**：GUI → 保险箱；用户若另设环境变量，平台优先级环境变量获胜（文档写明）。
4. **新增出站面**：本插件唯一的出站是用户配置的第三方端点——这是"委托"的代价，由用户自主决定信任对象。

### 12.1 P3 路由层设计（2026-08-16）

**用户决策**：① 默认服务商 = **Jina Reader**（免 API key，开箱即用）；② 回退机制 = **Jina Reader 兜底**；③ 预留客制化接口。

| 设计点 | 实现 |
|---|---|
| 默认适配器 | `DEFAULT_ADAPTER = 'jina'`（新安装/未配置时即用 Jina 匿名抓取） |
| 回退字段 | 设置新增 `fallback`（默认 `'jina'`）；主服务商失败时自动回退 |
| 回退触发 | 主适配器**抛错**（网络/解析/服务错误）或返回 **HTTP ≥ 400**（如 key 无效、限流） |
| 回退解析 | 回退适配器**始终用其自身默认**端点/key 引用（自定义 baseURL/key 属于主服务商）；Jina 兜底即匿名 |
| 预算 | 一次工具调用 = 一次预算（主+回退共用一次 acquire） |
| 双失败 | 抛出合并错误："主 X 失败（原因），回退 Jina 也失败（原因）" |
| 卡片 | 不暴露 fallback 字段（固定 Jina 兜底，架构已支持改）；服务商选择不变 |

**客制化接口预留**：
- **内置扩展点**：`ADAPTERS` 注册表（provider.ts）——加一个服务商 = 1 个适配器文件 + 注册表 + `KEY_ENV/BASE_URL_BY_ADAPTER` 两张表 + 卡片选项（机械步骤，文档化）
- **用户自建服务**：契约 v1（`docs/contract.md`）——n8n / 自建爬虫 / 自托管 Jina 按契约接入同一注册表（客制化专题落地）
- **路由组合**：`adapter`（主）+ `fallback`（兜底）是预留的提供方组合接口，未来可扩展为列表/回退链

**P3 验证记录**：headless 端到端——主=firecrawl（apiKeyEnv 指向不存在的引用→必失败）+ fallback=jina → **抓取成功**（证明回退生效）。
